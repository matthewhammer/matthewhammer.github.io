An Official Hazel JS Library?

Since 2026-10-20 a game in daily use, Messed Up Dress Up (MUDU), runs its rules in Hazel through a draft library, hazel-lib.js (#2711, with #2719 stacked on it). Should Hazel make such a library official: a supported way for any web page to analyze, run and show Hazel programs? This report lays out what the draft does, what the game has taught us, the uses beyond it, and the costs.

Short answers.

  1. What it is today: one script, 643 KB over the wire (2.7 MB unpacked; the full app is 1.7 MB), that puts window.Hazel on a page: analyze and run a text, analyzeProgram and runProgram for a program of named modules, with Hazel values coming back as plain JS values and JS functions going in and out both ways. Plus an embed mode: Hazel's own tiles in an <iframe>, showing (and, on a further branch, editing) a program the page posts.

  2. For: it already works for a real, typed, event-driven use; it is small to keep (one OCaml module and a doc over the existing evaluator); and it opens Hazel to every page that wants live, typed, hole-tolerant code: lessons, docs, games, other editors.

  3. Against: an API is a promise. It fixes how Hazel values look in JS, ties pages to builds that today are branch URLs with no versions, runs on the page's own thread, and puts an evaluator in pages that may run code they did not write.

  4. Suggestion: make it official in two steps: first merge #2711 and #2719 as an experimental library (labelled so, built on dev), then promise stability only for the small core (analyze, run, the value mapping) once a second user besides MUDU has used it.

What the draft library does

CallWhat it gives
Hazel.analyze(text){errors}: the program's error messages.
Hazel.run(text){errors, value}. Errors do not stop a run: Hazel evaluates around its holes, so the page decides which errors it accepts.

What the game has shown

MUDU's 📜 Scripting panel gives five kinds of room a rule each: a function from the game's event (a lever pulled, a way taken) to a tree of commands the game carries out (^report(33) describes the rules and their types). The same rules can be written in Hazel (the default), in JS, or in Fumola, which makes a fair comparison.

  • Types earn their keep. The rules' vocabulary is sums (Pull(L), Way(N), a room's exits), checked where a rule's parameter is annotated, so a rule that returns the wrong command is an error in the editor, not a bug in play. The JS version of the same rule has no such check.
  • Holes are a feature in a game. A rule half written still runs: the game falls back to its built-in behaviour while ok is false, so kids can edit while they play.
  • Calls cost more than they should. ^report(25) took one call apart: the World room's rule, 40 ms a call at a 16×16 map against 0.003 ms for the same rule in JS. Every call pays a floor that grows with its argument (8.5 ms at 16×16), because the library turns the JS argument into Hazel syntax and evaluates it back into the value it already was; and a typed helper re-checked its annotation on every step, which #2681 removes (144 ms to 20.6 ms). Passing the rule only what it needs made it flat (0.9 ms).
  • Reading can be slow. Reading the program is 21 to 81 ms for the panel's modules (well formed), but up to 1.8 s when a module has an unclosed bracket, because only the recovering parser can read it (its time grows with the square of the module's length). The first load of the library and its first analysis took about a second (the game's own log: "analyzed and run in 1148 ms").
  • What the game had to build itself: the outline of a program (modules, types, functions) from regexes over the text, and which row a click lands on. Modular editors (#2469) already know these; the open question on #2711 is how the library should take #2469 as a dependency.
  • Gaps found by use: constructors declared in one module were not usable in the next ("Constructor is not defined"), fixed separately by #2729; and a constructor from JS whose tag the sum lacks, which a fix kept on one laptop (js-library-tagcheck) makes stay stuck under its ascription.

For making it official

  • It is small and mostly done. One module over the existing statics and evaluator, a doc and tests. Merging costs little review; keeping it costs a test run.
  • It shows Hazel where people are. Hazel's ideas (holes that still run, typed edit states) are hardest to show in the abstract; a page that runs a kid's half-written rule is an easy demonstration.
  • Real use finds real bugs. MUDU's daily use found the module-constructor gap and the JS constructor check within days.
  • Official means findable. A stable URL and a version beat a branch build named in someone's code; today a page must point at hazel.org/build/<branch>/, which moves when the branch does.

Against, or costs to plan for

  • An API is a promise. The JS shape of Hazel values ({tag, value}, tuples as arrays, labeled tuples as objects) becomes hard to change once pages depend on it. Hazel's own types keep moving (modules, labeled tuples, type functions).
  • Versions and builds. Branch builds have no versions. An official library needs releases (a version in the file, Hazel.version already says "0.1 (draft)"), and a place that keeps old ones, or pages break when dev moves.
  • The call boundary. Converting a JS value by building Hazel syntax and evaluating it is the floor under every call (^report(25)); an official library should hand Hazel values in directly, and say how big an argument a call should take.
  • Size and the main thread. 643 KB is fine for a game, heavy for a docs page with one example; and the library runs on the page's own thread, so a slow analysis (the 1.8 s case) freezes the page. Hazel's app already has an evaluation worker; the library does not use one yet.
  • Running code a page did not write. A page that runs a visitor's Hazel program runs it with the page's own rights, as any in-page evaluator would. The library should say so, and a worker would help here too.
  • Two surfaces to keep in step. The embed frame is Hazel's whole app in a mode; every change to the app can change the frame. Its messages need the same care as the library's calls.
  • Team time. Someone has to own it: answer issues, review changes, decide what is in the stable core.

What next

  1. Ready #2711: move the stranded constructor fix onto it, bring its description up to date (the editor in a page moved to #2719 and beyond), and take it out of draft.
  2. Open a PR for the embed frame's 12 commits (embed-editable), stacked on #2719, so the whole of what MUDU uses is under review.
  3. Decide the #2469 question (outline and navigation from modular editors) before the library grows its own.
  4. Convert JS values directly into Hazel values at the call boundary, not through syntax re-evaluated (^report(25)'s floor), and merge #2681, which the game's typed rules need.
  5. Run analysis in a worker in the library, as the app does, so a slow read never freezes a page.
  6. Version it: a build per release at a stable URL, Hazel.version a real number, and the stable core named in the doc.
  7. Find a second user (a course page, or the docs' own examples) before promising stability beyond the core.
