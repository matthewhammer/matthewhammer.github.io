What #2651 changes

In Statics.re, the ModuleExp case (line 2754 on dev; the diff: #2651's files):

  • module M = def in body is analyzed by expanding it to a let. The let's analysis walks def once, and records an InfoExp for it in the info map, keyed by def's id; its elab_term is def's elaboration.
  • Before: the ModuleExp case then walked def a second time, directly (go(~ana=def_ana, def, m)), only to get def_elab_direct for ModuleHelpers.moduleexp_elab. That walk also re-recorded the info of every node inside def, and its entries won.
  • After: it reads elab_term back from the info map (Id.Map.find_opt(Exp.rep_id(def), m)). The direct walk stays as a fallback when no info was recorded, and (the second commit, 29c08fd8fa) when def names its own module: the let then wrapped def in a FixF fixpoint and analyzed it with M in scope, so the direct walk runs again and reports M as unbound, as before.
  • Cost: a nested module's definition was walked twice at every level, so 2depth times for the innermost one; after the PR, once per level by this case.

Review points from reading the code

From reading the code at the two commits above. The first is confirmed by the PR's own tests; the others are not yet fact-checked, and the full report checks each one.

  1. One behaviour change, pinned by the PR's new evaluator test, and a fix (Alexander confirms dev's result is a bug from the auto-labelling; see question 1) (Test_Evaluator_Modules.re): module M : { let x : Int } = { let x = 1; let y = 2 } in M.x evaluated to the whole unelaborated module before; with the PR it evaluates to 1. The cause, by reading: the singleton-label lift in statics records one elaboration in the info map and returns another, the only path where the read-back differs from the direct walk.
  2. Why the read-back is the same elsewhere: in the let's non-recursive branch, the let's walk of def and the old direct walk get the same context, the same expected type (the ascription's type, or syn), the same term and the same filters; only the ancestors list differs (the module's id appears twice, as it already does for the body). So the PR description's "add records exactly the elab_term it returns" holds on every path that ends in add.
  3. The self-naming check reads the shape Let(_, FixF, _) of the let's elaboration. If the let case ever wraps the fixpoint differently, the check turns false silently, and the error disappears again; the let's info co-context names the module when def mentions it, a more explicit signal.
  4. The "no info recorded" fallback looks unreachable: every walk of a node records an InfoExp at its ids. It is a defensive branch.
  5. The infos inside def now come from the let's walk, not the direct one: in a function-valued module that does not name itself, their context includes the module's own name, so the cursor inspector or completion could offer it there. Elaboration does not depend on it.
  6. Pass count: on today's dev every let also runs a recursion probe first, so a module binding goes from three walks of def to two; to one with hazelgrove/hazel#2603 (a let analyzed once unless it refers to itself). The two merge cleanly.
  7. Tests: the self-naming test passes on any static error anywhere; pinning it to F's id and kind would make it exact, and module F : Int -> Int = fun x -> F(x) in 1 would cover the fallback's ascription arm.
  8. Merge readiness: the branch is behind dev but merges cleanly; updating it so CI runs on today's dev is a cheap last check.

Questions for Alexander

Alexander: this section stands on its own. hazelgrove/hazel#2651 stops the ModuleExp case in statics from analyzing a module's definition a second time: it reads the definition's elaboration back from the info the expanded let recorded (what changes). These questions need your knowledge of Modules II (hazelgrove/hazel#2493, #2494, #2495). Drafts: each is being checked against the code, and the full report's version replaces these.

1. Is M.x = 1 the intended runtime meaning of a module under a signature it does not satisfy? answered

module M : { let x : Int } = { let x = 1; let y = 2 } in M.x is a static error (the signature does not admit y), but it still runs. Before #2651 it evaluated to the whole unelaborated module; with #2651 it evaluates to 1, and the PR's new evaluator test pins that. Is 1 what Modules II means, or should this run differently (or not at all)?

Answered, Alexander, 2026-10-21: dev's result is a bug, from the auto-labelling of single-member tuples; the program should evaluate to 1 or be stuck. So #2651's 1 is a correct result, and its test pins it.

2. Are modules meant to be recursive? answered for now for Cyrus

At expression level, module F = fun x -> F(x) in 1 is an error (F is unbound inside its own definition), and #2651's second commit keeps it one, with a test whose comment says "modules are not recursive". By reading (not yet checked), a module item inside a module body, { module F = fun x -> F(x) }, is lowered to a plain let in ModuleHelpers, which would analyze it recursively with no error. Which behaviour is intended, so the test pins the right one?

Answered for now, Alexander, 2026-10-21: not settled; for now it is fine for modules not to be recursive by default, since recursion has a number of known correctness problems. Whether they should be is a question for Cyrus. So #2651's test, which pins the expression form as not recursive, matches the current intent; the module-item form inside a module body stays as it is until then.

3. Which signal should say "this definition names its own module"? answered for Cyrus

#2651 detects it by the shape of the let's elaboration, Let(_, FixF(...), _). That ties the ModuleExp case to where the let case puts its fixpoint. Would you rather it read the module's name from the let's co-context, or is there a signal in Modules II that is meant for this?

Answered, Alexander, 2026-10-21: Modules II has no signal for this, and he did not write the original module keyword. As things stand, module is a non-recursive let. His suggestion: give the let analysis an argument saying whether to check the recursive case, so that a module binding is never analyzed recursively. With it, the let would report a self-reference as unbound by itself, the FixF shape check and its fallback would not be needed, and a module binding would skip the let's recursion probe too.

He also raised two design questions, for Cyrus: whether a module binding of something that is not a module (module F = fun x -> 1 in F(3), accepted today) should be a static error, as he expects; and the module keyword itself, where he had favoured plain let for module definitions and Cyrus wanted the keyword to do more.

4. What is ModuleHelpers.moduleexp_elab meant to drop from the let's elaboration? answered

It rebuilds the module's elaboration from the definition's own elaboration (def_elab_direct), without what the let wraps around it: label alignment, a function name and, for a definition that refers to itself, the FixF. #2651 takes that elaboration from the let's recorded info rather than a second walk. Is "the definition's elaboration before the let wraps it" exactly the contract, so that the read-back meets it?

Answered, Alexander, 2026-10-21: yes, as he understands it, and it comes from the old elaborator. Reading the definition back from the stored info is closer to the original design than dev's second pass, because the old elaborator also read the definition from the statics map.

5. Any order you need with your Modules II parts 2 and 3, and with #2603? answered

#2651 touches only the ModuleExp case of Statics.re and adds two tests. It merges cleanly with dev today and with hazelgrove/hazel#2603 (a let analyzed once unless it refers to itself), which together bring a module binding to one walk of its definition. Does anything in flight in Modules II change this case?

Answered, Alexander, 2026-10-21: #2651 does not conflict with Modules II in substance (he has not yet looked at #2603). Checked with git merge-tree: #2651 merges cleanly with part 1, and with each of parts 2 to 9 conflicts on one line, the fallback's direct pass, where part 2 added ~coercible=true. On part 2 the let analyzes the definition with ~coercible=true as well, so the read-back reads the same analysis, and the resolution is to add ~coercible=true to the fallback.
