hazel-jit: Livelit Views Compiled to JavaScript

How much faster can a livelit's view run as JavaScript compiled from its Hazel, instead of on Hazel's interpreter? Decided at the meeting with Cyrus on 2026-11-05, as the best case first: JS's numbers allowed to differ from Hazel's for now (^ticket(694)). This report follows the work as it goes, for the next meeting on Wednesday 2026-11-11 at 10:00 Mountain, where it is item 2 of the agenda, ^report(42).

Outline#

  1. How much faster: a render of the Polygons slide's view, on the interpreter and compiled, its first renders and once warm.
  2. Where the time goes now: the trip back, the view's answer made again as Hazel terms, is most of a compiled render; the trip in is small.
  3. How it works: the compiler, how Hazel's values look in JS, and the trip in and out.
  4. In the app: where the compiled view runs, the setting, and what happens when it cannot.
  5. Does it give the same answers: the tests, and checking that they can fail.
  6. What it does not do yet.
  7. For Wednesday's meeting: the agenda's questions about this work.
  8. What next, and how this was put together.

How much faster#

A render of the Polygons slide's view takes 14.6 ms on the interpreter and 0.43 ms compiled, about 34 times faster, counting the trip into JS and back, once Node has warmed up to it. The first 30 renders after compiling take 1.13 ms (their median), about 13 times faster: the first took 5.72 ms, and they fall to about 0.44 ms while Node optimizes the way back. The compiled code itself takes 0.045 ms of that, about 324 times faster than the interpreter. Smaller programs gain more, since there is no trip to take: the Petri net rule of ^report(43), answering four events, 6.47 ms against 0.015 ms (446 times), and a recursive sum of 1,000 numbers, 46.5 ms against 0.031 ms (1,482 times).

Update, 2026-11-06 19:00: the first version of this report said a render was about 16 times faster. Those renders were timed first and cold, the first 30 after compiling, and their times fell from 2.1 ms to 0.4 ms over the 30 runs as Node optimized the way back, so their median measured the warm-up more than a render. Each series is now timed after 10 untimed runs. Warm, a render is about 34 times faster; the first renders, timed cold as before, are a row of their own (^ticket(694)).

These are Node's numbers, from a development build, on one laptop, medians of 30 runs in one test session; the runs vary (the Petri net rule's interpreter time ran from 4.8 to 9.2 ms over the day's test sessions), so read the ratios to within a factor of two. The interpreter's numbers do not include the call memo the app gives a view (^report(1)'s CallMemo), which saves calls repeated between renders; compiling the definition took 3.97 ms, once. Browser numbers, and a release build, come next.

Where the time goes now#

The trip back is 83% of a compiled render: 0.35 ms of 0.43. The trip in takes 0.031 ms (7%) and the compiled view 0.045 ms (11%), so the way back costs about 11 times the way in, and about 8 times the view itself. Each step was timed alone, warm, and the three add up to 0.43 ms, about the whole render's time.

Why the way back costs more: there is more of it. The compiled view needs its model as JS values, so the model is converted on the way in; and the app draws a Hazel value, so the view's whole answer, its command and every node of its Html tree, is made again as a Hazel term on the way out. The slide's model is 115 nodes (cons cells, tuples, constructors and the numbers and strings in them); the answer is 861, about 7.5 times as many, with 7 event handlers, none of them capturing a value. Per node, the way back costs a little more: 0.41 µs a node, against 0.27 µs a node in.

Almost half the way back is making ids. Each Hazel term carries an id, and each term the way back makes gets a fresh one, a random UUID (0.17 µs each). The trip back makes 906 terms, and 906 fresh ids alone take 0.16 ms, 45% of the trip back. Terms that are only drawn, and never edited, might not need fresh ids; whether anything in the app reads them is the open question under what it does not do yet.

Ways to make the way back cheaper, not tried yet: give the terms it makes cheaper ids; keep the answer in JS until it is drawn, so the part of the app that turns it into the page's elements reads JS values directly; convert lazily, only the parts that are read; or keep what did not change since the last render, as the call memo does for the interpreter.

How it works#

hazel-jit turns an elaborated Hazel term into the source text of a JS function, once, and the browser's own JavaScript engine runs it. HazelJit.compile_full, in src/language/dynamics/HazelJit.re, walks the term Hazel's elaborator makes (the same term the interpreter runs) and writes JS, which is made into a function with new Function.

Hazel's values in JS. Numbers are JS numbers (so Int overflow and rounding are JS's: the best case first); a list is cons cells ({h, t}, with null for the empty list), so :: takes constant time; a tuple is a JS array, each labeled component also a property by its label, so p.x is a property read; a constructor is {c: "Name", v: payload}; a function is a JS function of one argument; a module is a labeled value of its members, in order. A let or a case binds JS variables declared at the top of the enclosing function, each with a name of its own, so the code is expressions all the way down and no closure is made for a let. Types, ascriptions and parentheses are erased. Builtins written in OCaml have JS versions by name; builtins written in Hazel are compiled once, before the program's code.

What it does not compile, it says why, and that code runs on the interpreter: holes, tests, quotations and splices, projectors, partial application. A member of a module that does not compile (a livelit's expand, say) becomes a stub that says why if it is called, so the rest of the module still compiles.

The trip in and out (HazelJitValue.re). Into JS is direct: each Hazel value as above. Back is harder, in two ways. A JS number does not say whether it was an Int or a Float. So the compiler records each constructor's type as the elaborator gave it, and the type aliases the term defines, and the way back reads a number by the type expected where it sits: a constructor's argument at its argument's type, through aliases. A whole number with no type to go by comes back an Int. A function in the answer, an event handler like Attr.on_input(fun v -> SetName(v)), has to come back as a Hazel function the interpreter can apply when the event comes. So every compiled function carries the index of the Hazel function it was compiled from and the values it captured, and comes back as that Hazel function closed over those values (the compiler notes, for each function, which outer variables its body uses).

In the app#

Livelits' views run compiled in the app, behind a setting that is on by default, and the interpreter runs any view hazel-jit cannot. LivelitProj.eval_view compiles each livelit definition once (kept by its term), calls its compiled view on the model, and hands the command it returns to the code that runs view commands and draws their Html, as before. When the compiled view answers, the definition is not evaluated by the interpreter at all on that render.

  • The setting is Compiled views, in the settings menu, on by default; off, every view runs on the interpreter as before.
  • When it cannot (a form it does not compile, a recursive function in the answer, an error while running), the view runs on the interpreter, the browser's console says why, once for each reason, and that definition is not tried again.
  • Not checked in a browser yet. The tests run the same code in Node; trying it on the slides is the next step.

Does it give the same answers#

Yes, on every program tested, and the tests catch a broken compiler. test/Test_HazelJit.re has 37 tests, all passing at 7a7151443c: 24 small programs whose compiled results agree with the interpreter's (arithmetic, floats, recursion, tuples and labels, lists, constructors, options, strings, equality, closures, nested patterns, modules, builtins, and the Petri net rule); the Polygons slide's view, its whole Html tree equal to the interpreter's; values carried back as the interpreter's own (whole floats staying floats, a type alias, labels with no type, the Petri net's commands); a view and an event handler through the trip in and out, the handler then applied by the interpreter; and the Polygons view through it. Breaking the compiler on purpose fails them: compiling Int's + as - failed 5 of 18 programs; reading numbers without their types failed 3 tests; dropping the values a function captures failed the handler test.

What it does not do yet#

  • Numbers are JS's. Int overflow, division and rounding may differ from Hazel's: allowed for the best case, to be decided before anything ships.
  • The call memo, probes and the step budget do not apply inside a compiled view: no reuse of repeated calls between renders, no probe's samples from inside the view, and a deep recursion is JS's stack, not Hazel's step limit (a stack overflow falls back to the interpreter).
  • A recursive function in a view's answer is refused (a Hazel closure cannot hold a cycle as a plain value), and so is a JS builtin passed as a handler.
  • Values made again on the way back get new ids; whether anything in the app depends on a model's ids surviving the trip has not been checked.
  • One slide measured. Full Body, the Witch, Hands and the Scenes slide's woods, the slides with the most polygons, come next.
