Hazlets, So Far

A Hazlet is a JavaScript program whose event handlers are written in Hazel: the program hands an event to a Hazel function, and acts on what the function answers. Matthew's word for the pattern (2026-11-02). Messed Up Dress Up, a game for kids, is the first Hazlet and so far the only one. This report gathers in one place what has been built for Hazlets since 2026-10-20, where each piece stands today, and what comes next. Matthew asked for it on 2026-11-03, for his meeting with Cyrus on 2026-11-04 (^report(37), the agenda, its section 2).

Short answers. Each is as of 2026-11-03; the sources are at the end.

  1. One Hazlet runs today, live. Messed Up Dress Up's 📜 Scripting tab (since 0.0.412, 2026-10-24) holds a Hazel program of modules: 📚 Common, then one module per room that has logic, five rooms in all. Each room's on_event : (Globals, Event) -> Cmd answers the game's events, and each room can be run by Hazel, by Fumola or by the game's own JS (Figure 1).

  2. Nothing of it is in Hazel's dev branch yet. The library the game uses, hazel-lib.js, is on two draft PRs, #2711 and #2719, both with CI green; GitHub reports that #2711 now conflicts with dev. The tiles a player edits in are on a branch with no PR, embed-editable. The game loads both from branch builds (the table).

  3. The library is on npm, as hazeljs 0.0.1, since 2026-11-02 at 11:03 MST: one file, entry points for Node and for a script tag, TypeScript declarations and a README. A fresh project installs it from the registry and runs the README's examples. It is built from #2719's head, so it carries none of dev's changes since 2026-10-19 (below).

  4. A Hazel rule is fast enough for a lever, with one pause. In the game, a Hazel rule answers in about 3.5 ms of a 13.7 ms lever pull (Fumola about 1.6 ms, of 10.7). But the first event after a reset waits 0.5 to 0.7 s while the program is built (^report(32), a draft). Larger rules pay for crossing the boundary, and the fixes for that are on trial branches, not in the game (below).

  5. Next: the package's checks, its placeholder version and a home for its source; the game loading Hazel from the package; the trap room live in ^report(34), its rule edited in tiles; and the library's road to dev, which is the meeting's question (What next, For the meeting).

What a Hazlet is#

Many JavaScript programs are organized around events: a click, a key, a timer, a message. A Hazlet hands some of those events to Hazel. The JS side builds a value describing what happened and what the handler may see, calls a function written in Hazel, and gets back a value describing what to do. Hazel never touches the page directly: its answer is data, and the JS program acts it out. Two names keep the parts apart. The library (hazel-lib.js, which defines window.Hazel) is the API for analyzing and running Hazel from JS. A Hazlet is a program that uses the library this way, with Hazel functions as its handlers.

In Messed Up Dress Up, a red lever pulled in the castle's trap room is the event Pull(L). The game builds the room's view of its state, a Globals record (the levers, how the pits are wired, the game's random draws, and more), and calls TrapRoom.on_event. The rule answers a Cmd, a chain of commands such as Flip(L, SetPit(0, true, Done)): flip the lever, then open pit 0. The game plays each command as its own code would, with its animation and its pits. When the player edits a rule in the 📜 tab, the game hands every module's text to Hazel.runProgram, which builds the one program and reports errors, holes and unfinished brackets module by module. While the program has errors or is not finished, the rooms run the game's own JS, so the game keeps working; the Hazel rule still runs as far as its errors allow, and its answer goes in the event log beside them. Each Hazel box shows its module in Hazel's own tiles, from Hazel's app in a frame, with Hazel's error marks; an edit made in the tiles is posted back to the game.

^report(33) reads what the rules are told today in detail: a view built for each room, with numbers for names. It proposes names for every place and thing in the game, and types built on them.

How fast it is#

  • A lever, in the game (^report(32), a draft, 60 pulls each in a browser): a Hazel rule answers in about 3.5 ms, a Fumola rule in about 1.6 ms. The commands then take the game about 9 ms either way, so a whole pull is 9.7 ms with JS, 10.7 with Fumola and 13.7 with Hazel, under a 60 Hz frame. Hazel's one slow event is the first after a reset, 0.5 to 0.7 s, while the program is built; Fumola's slowest is 12 to 21 ms. Hazel's tiles take about 3.7 s to fill all six boxes, while the page keeps drawing.
  • Crossing the boundary (^report(25), in Node): the library turns the whole JS argument into Hazel syntax, gives every node a fresh id, and evaluates it back into the value it already was. For the World rule's argument at 16×16 that floor is 8.5 to 10.6 ms a call, whatever the rule does.
  • On trial branches (^report(30), on GitHub's runners): with closures kept across the boundary, lists not re-typed in loops, a big value crossing once as a handle, and values skipping the evaluator's stages, a World move went from 241 ms to 0.97 ms. None of these are in the library the game loads.

The npm package, hazeljs#

A first, experimental release: npm install hazeljs, or a script tag from jsDelivr or unpkg. Version 0.0.1 has 9 files, 2.8 MB unpacked (about 640 KB gzipped). require("hazeljs") and import Hazel from "hazeljs" give the same Hazel object that a script tag puts on the page. The package also has TypeScript declarations for the API and the values, and a README that npmjs.com shows. The README covers install, the API call by call, the values table, programs of modules, size and speed, limits, and the game as a use case. It sends readers to hazel.org and to the contributors on GitHub for who makes Hazel. The name, hazeljs, is Matthew's choice; Hazlet stays the pattern's name. License MIT, as Hazel's.

What it is built from: #2719's head, 0d66c36618, which is dev of 2026-10-19 plus the library's own 11 commits. There are no modular editors (#2469), no livelits, and none of the performance PRs still open against dev. As of 2026-10-29 the release was 151 commits, 24 PRs, behind dev (^report(34) lists them).

Measured, in Node 22 on a laptop (the README): require about 170 ms; a small program run about 30 ms; a module of 100 short members analyzed in about 110 ms, of 400 in about 2.3 s.

Known issues, in its CHANGELOG: a module of about 150 members overflows Node's default stack; the result's ms field reads 0 under Node (a bug in the library's timing, not yet traced); a text only Hazel's slower, recovering parser can read prints a SLOW PARSE line to the console. Also open: npm lists a placeholder it made first, 0.0.0-stage, to be deprecated; and the package's own source is not yet in a public repository.

What next#

The package#

  1. The checks: a browser page and a TypeScript example (checked by tsc --noEmit), and a GitHub workflow that packs the package, installs it into each example as a user would, and runs them, the page in headless Firefox (^ticket(672)).
  2. Deprecate 0.0.0-stage. Decide where the package's source lives (a folder on #2711's branch, built by dune, or a repository of its own), how versions after 0.0.1 name the Hazel commit they are built from, and whether it moves to an @hazelgrove organization on npm (^ticket(673)).
  3. The game loads Hazel from the package, pinned to a version, so the game is the package's first real user; its speed run is the check (^ticket(674)).

The trap room live in a report#

Matthew's ask (2026-11-02): a reader plays the trap room on ^report(34)'s page and edits its Hazel rule in tiles, the room answering each edit at once (^ticket(675)). Three pieces, in order:

  1. The trap room outside the game: first a link that opens the game at the trap room with its 📜 tab showing and Hazel chosen, so a report can frame it; later the room as a package of its own, which means pulling it out of the game's shared state (^ticket(676)).
  2. Tiles in a page: a PR for embed-editable, stacked on #2719, and a place to serve it from that a report can frame (^ticket(677)). The library package has no editor.
  3. The wiring: the report's page posts the room's module text to the tiles, takes each edit back, runs it with hazeljs, and hands the new on_event to the room (^ticket(678)).

The library, toward dev#

From ^report(34)'s list, still open:

  1. Ready #2711: resolve its conflict with dev, bring its description up to date, take it out of draft.
  2. Open the PR for embed-editable (the same step as above), so all that the game uses is under review.
  3. Decide whether the library's programs take their outline and navigation from modular editors (#2469) before the library grows its own.
  4. Convert JS values straight into Hazel values at the boundary, rather than through syntax evaluated again (^report(25)'s floor), and land #2681, which the game's typed rules want.
  5. Run analysis in a worker inside the library, as the app does, so a slow read never freezes a page.
  6. Find a second Hazlet, a course page or the docs' own examples, before promising stability beyond the core.
